## Instructions

`bin/rails assets:precompile` boots the app during the image build, and that
leaves an empty `storage/production.sqlite3` in the image. Docker copies an
image's files into a named volume the first time the volume is mounted, so a
brand-new deploy starts with that file on its storage volume. `db:prepare` then
treats the databases as existing and runs migrations instead of loading the
schemas; the queue, cache, and cable databases have no migrations, so they stay
empty and Solid Queue crashes on boot (Puma exits with "Solid Queue has gone
away" and kamal-proxy answers 502).

1. In the `Dockerfile`, end the `assets:precompile` step by removing any SQLite
   files it left in `storage/`:

   ```dockerfile
   RUN SECRET_KEY_BASE_DUMMY=1 ./bin/rails assets:precompile && \
       rm -rf node_modules && \
       rm -f storage/*.sqlite3*
   ```

   Keep whatever else the app's step already does; only the final `rm -f` is new.
2. An app already running in production needs nothing else: its volume already
   holds real databases, and `db:prepare` keeps working as before.
3. An app whose first deploy already crashed this way: load the missing schemas
   once, then restart the web container:

   ```sh
   bin/kamal app exec "env DISABLE_DATABASE_ENVIRONMENT_CHECK=1 \
     bin/rails db:schema:load:queue db:schema:load:cache db:schema:load:cable"
   ```

4. Set `template_version` to at least `"0.8.1"` in `.template-manifest.yml`,
   never lowering a newer value.

## Verify

- A freshly built image has no SQLite file in storage:
  `docker run --rm --entrypoint sh <image> -c "ls storage/"` lists only `.keep`.
- After the next deploy, `/up` answers 200 and the web container's restart
  count stays at 0.
